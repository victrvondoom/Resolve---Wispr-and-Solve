The failure it fixes

Automation usually breaks quietly, between the words and the effect.

One request: Prepare a follow-up for Jordan Lee using the latest report, update the CRM and send it after I approve. Three ordinary things go wrong.

Two Jordan Lees

The CRM has two contacts with the same display name. A naive agent writes to whichever row comes first.

RESOLVE: stops with NEEDS_CLARIFICATION, shows stable IDs and context, and binds the choice by ID, never by name.

The report changed after approval

You approved one file. Before the send, someone edits it. Most pipelines attach whatever is on disk now.

RESOLVE: approval is bound to a digest of recipient, content, attachment SHA-256 and intent revision. A changed file no longer matches, so the send is refused.

The acknowledgement got lost

The send goes through but the response never arrives. A stateless agent retries, and the email goes out twice.

RESOLVE: persists DISPATCHING first, marks the outcome UNCERTAIN, and reconciles by reading the outbox. It does not retry blindly.

How it works

Intent–Entity–Effect Continuity, recorded in a Causal State Ledger

Hypothesis (IEEC): an agent is safe to trust with consequential actions only if every action carries an unbroken chain from the user's current intent revision to a stable entity, a pinned version, and an effect that is checked independently. The Causal State Ledger persists each link and every state transition in SQLite, so the chain survives restarts and can be streamed live.

  1. 1

    Capture intent

    Typed or dictated text becomes a mission with a numbered intent revision. Speech is reviewed before it is submitted.

  2. 2

    Resolve entities

    Candidates are found by name, then bound by stable ID. Ambiguity stops the run and asks you.

  3. 3

    Pin versions

    The latest report is chosen by modification time and pinned by SHA-256, not by file name.

  4. 4

    Approve the exact action

    You approve a digest of the action. Change any part of it and the approval no longer applies.

  5. 5

    Act through a real tool

    An executor holding a lease drives the fixture apps through Playwright. DISPATCHING is written before any side effect.

  6. 6

    Verify independently

    A verifier reads the app's own database to confirm the effect, or reconciles an UNCERTAIN outcome read-only.

Honest status

What is verified, and what is not

“Verified” means real input, a typed contract, a real tool, an effect observed outside the generating code, an independent verifier, and an automated test that can fail.

Verified on Linux

Browser fixture missions

CRM, reports and outbox apps driven by Playwright (DOM-level, not physical cursor). Effects checked in each app's SQLite database.

Verified on Linux

Approval digests

A wrong or stale digest is refused with 409. Editing the report after approval blocks the send.

Verified on Linux

Lost-ack reconciliation

A dropped acknowledgement becomes UNCERTAIN, then CONFIRMED by a read-only check. Exactly one message.

Verified on Linux

Executor lease

Two concurrent missions serialize on one exclusive lease. A fenced worker sends nothing.

Verified on Linux

SSE ledger stream

Persisted ledger events stream over Server-Sent Events and resume by sequence number after a reconnect.

Not run on build host

Native Windows control

Cursor movement, clicks and typing into Notepad were not exercised here: WINDOWS_NATIVE_TESTS_NOT_RUN on the build host. To test, run scripts/smoke-windows.ps1 in an interactive Windows session.

Simulated

Message delivery

The outbox is a local fixture: SIMULATED DELIVERY. No external email or messages are ever sent.

No integration

Wispr Flow

Wispr Flow was used to dictate development notes. There is no Wispr SDK integration in RESOLVE. Voice input in the app uses the browser's speech recognition where available.
