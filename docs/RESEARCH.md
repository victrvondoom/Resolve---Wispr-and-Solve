## Hypotheses and failure chain

The brief's H1–H10 follow a common chain: voice ambiguity can bind the wrong alias/entity (H1), application records can be stale or version-divergent (H2), a user revision can supersede a plan (H3), an ambiguous acknowledgment can cause a duplicate (H4), concurrent actors can conflict (H5), click success can be mistaken for business success (H6), recorded steps can lose semantic constraints (H7), screenshots can go stale after focus/state changes (H8), evidence can refer to a prior action (H9), and approvals can be detached from the reviewed action (H10).

For each, the minimum useful experiment is represented in the current slice as a focused deterministic check: duplicate-name resolution returns alternatives (H1); explicit report version policy uses modified time (H2); revision compare-and-swap invalidates old action (H3); ledger crash recovery leaves dispatching work UNCERTAIN (H4); cursor input uses a process-local exclusive lock and HWND foreground recheck (partial H5/H8); outbox verification reads a separate persisted result rather than the input dispatch response (H6/H9); semantic skill recording is not implemented (H7); action digest and revision are checked at approval (H10). These checks do not constitute the complete adversarial benchmark requested.

## Novelty statement

Confidence that the broad concept is novel: **low**. Clacky already overlaps voice-first real Windows control; winapp/pywinauto cover UI automation and cooperative turns; Microsoft verifier research and StateAct cover outcome checking; Iterate work covers comparable CRM/outreach settings. A defensible future claim, pending benchmark evidence, is: “an experimentally evaluated integration of typed intent revisions, ambiguity-aware entity/version binding, pre-dispatch desktop state guards, a durable uncertain-effect ledger, and independent local outcome reconciliation.” This repository currently implements only a small local prototype of that integration and has no comparative benchmark results.

Wispr Flow is treated as a way to dictate development prompts/instructions, separate from product voice input. This review did not establish an official Wispr API; RESOLVE does not claim one.
