## Error analysis / caveats
- Bug found by the benchmark itself and fixed: the CRM fixture replied before committing its SQLite transaction, so a fast client could observe "no task" right after a 200 (one B run was mislabelled false_success). Fixed by committing before replying (apps/web_fixtures.py); rerun numbers above.
- Scenarios were built to target each mechanism and the baselines are ours; results show necessity in these cases, not field reliability. Oracle (ground_truth tables) shares no code with the runner/verifier. Latency per run is recorded in `seconds`; there are no LLM calls (cost 0).
- Not covered: popup focus theft on Windows, swapped tabs, low disk, network loss, model outage (no model), screenshot redaction.
